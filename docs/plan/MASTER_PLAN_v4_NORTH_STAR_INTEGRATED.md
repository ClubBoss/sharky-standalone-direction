## 1. Product Thesis

### Product / Brand North Star

> The poker coach that turns mistakes into corrected table instincts.

### Operational North Star

> Turn a learner's poker mistake into a corrected decision that transfers to a
> new table spot and still holds later.

### Internal learner loop

`SEE -> DECIDE -> UNDERSTAND -> REPAIR -> PROVE -> TRANSFER -> RETAIN`

- `SEE`: independently notice the relevant table signal before an answer.
- `DECIDE`: commit from the available information.
- `UNDERSTAND`: grasp the causal reason, not only the verdict.
- `REPAIR`: identify and correct the misconception that produced the error.
- `PROVE`: demonstrate the correction with reduced scaffold.
- `TRANSFER`: apply it to a materially different situation without leakage.
- `RETAIN`: reproduce it after meaningful elapsed time.

Automaticity is not a separate milestone. It is a later quality of the loop:

`correct transferred decisions + reduced decision latency + no loss of accuracy`

### Learner transformation

Before: isolated rule recognition, wording/option guessing, post-answer clue
recognition, same-example success, and fragile recall.

After: independently notice the signal -> decide -> explain causally -> identify
the misread -> repair -> prove with less scaffold -> transfer -> retain ->
eventually apply outside authored Sharky prompts.

This transformation outranks feature count, lesson count, PR count, and
architecture completeness.

### Continuity-first invariant

Preserve meaningful current progression before globally redirecting a learner
toward a weakness. Interrupt continuity only when evidence proves that doing so
is more useful. This donor-derived invariant does not reactivate a donor planner
or a second personalization architecture.

## 2. Evidence and Claim Hierarchy

| Evidence class | Meaning |
| --- | --- |
| `MACHINE_PROVEN` | Deterministic source/tests/fixtures/telemetry/native evidence prove the mechanism. It does not prove a human learned. |
| `HUMAN_PROVEN` | Eligible real-human observation proves the bounded human claim actually tested. |
| `LONGITUDINALLY_PROVEN` | Human evidence across meaningful elapsed time proves persistence. |
| `MARKET_PROVEN` | Real market behavior proves the named demand/value/payment claim. |
| `REAL_POKER_PROVEN` | Unseen, realistic, or independently sourced poker decisions prove improvement outside authored Sharky prompts. |

Evidence classes are not interchangeable.

### No aggregate readiness score

No global numeric readiness score may substitute for evidence class. Historical
`94/100`, `99/100`, weighted scores, or counts of closed waves can be
prioritization artifacts only.

For each major North Star capability record:

1. strongest proven evidence class;
2. unresolved claim;
3. next valid evidence source.

### Prohibited proxy proof

None of these proves a learner outcome by itself:

- PR count;
- lesson/task/world count;
- green CI;
- screenshots;
- telemetry volume;
- XP/streak/time spent;
- `AI` naming;
- number of personalization systems;
- solver availability;
- visual polish;
- same-task correction alone;
- synthetic/AI novice simulation.

## 5. Gauntlet Operating Model

For every Gauntlet:

1. define the North Star claim;
2. define the falsifier;
3. define the required evidence class;
4. measure current behavior;
5. prove the bottleneck is real;
6. decide explicitly whether implementation is needed;
7. choose exactly one bottleneck/owner family;
8. choose the cheapest valid intervention;
9. implement the smallest sufficient change, if any;
10. deterministic proof;
11. native proof where applicable;
12. Human/longitudinal/market/real-poker proof when required;
13. update the scorecard;
14. choose exactly one: `CLOSE`, `ONE_BOUNDED_ITERATION`,
    `CHANGE_HYPOTHESIS`, `DEFER`, `DO_NOTHING`;
15. refreeze closed boundaries.

Rules: evidence before implementation; one active bottleneck family;
`DO_NOTHING` is valid; no PR-count roadmap; no implementation because a phase
exists; no proxy metric outranks learner outcome.

## 8. Learning-Efficacy Gauntlets

These are evidence-driven candidate families, not guaranteed implementation
waves. Existing machinery is tested first.

### Transfer - MUST

Question: can a corrected concept transfer to a materially different table
situation without leakage/coaching?

Change enough context to prevent memorization; use reduced scaffold; do not
pre-highlight answer-bearing clues. Mechanism is `MACHINE_PROVEN`; learner
outcome is unproven.

### Automaticity - quality of transfer

Measure `correctness + decision latency + no loss of accuracy` inside successful
transfer. Do not create an automaticity architecture project unless evidence
proves existing machinery cannot answer the question.

### Day-2 / Day-7 retention - MUST

Test the existing 24h/72h/7d mechanism with real learners first. No new
scheduler unless learner evidence proves the current mechanism fails.

`docs/plan/DURABLE_RETENTION_TRANSFER_CONTRACT_v1.md`

success; outcome lift is.
