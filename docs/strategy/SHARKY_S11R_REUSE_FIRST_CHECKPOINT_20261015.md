## Owner intent

Stop inventing non-differentiating engineering infrastructure when a mature, maintainable, legitimately reusable solution exists. Concentrate bespoke Sharky work on trustworthy poker decisions, actionable causal feedback, honest assistance-aware repair, persistent progress and earned/elapsed learning proof.

**Default rule for future admitted implementation waves:** `REUSE -> ADAPT -> BUILD`, but only after compatibility, total integration/maintenance cost, license and learner-truth review. A familiar third-party package is *not* automatically a lower-risk solution. `DO_NOTHING` and keeping a working component are valid outcomes.

## Exact bounded mission

**Timebox: 2–4 hours total of research/evaluation**, not a new 1–2-day implementation mission. No new app/source dependencies, code changes, native gauntlets, visual replacement or additional QA writers during this checkpoint.

Prioritize at most **three concrete current opportunities**, selected using actual S11 cost and upcoming S12.V risk rather than general curiosity:

2. **Visual/interaction components and licensed assets:** survey cohesive Flutter-ready primitives and lawful visual reference patterns relevant to *specific* S12.V falsifier hypotheses. Study only; do not decide table reconstruction, copy competitor art or re-open protected PR #224.
3. **Existing support libraries/reference implementations** where custom code is non-differentiating (e.g. serialization, robust persistence, test oracles). Compare against the **already integrated** packages and established source-owned contracts; no wholesale replacement of XP, assessment, repair, spaced retention or progression on speculation.

Reuse the finished S03 competitive benchmarks and dated research; this checkpoint is **technical component sourcing**, not another S03 competitor/UX strategy study.

## Candidate evidence matrix (one page, maximum three decisions)

For each high-value candidate, provide:

| Field | Required proof |
| --- | --- |
| Learner/engineering job | Concrete current source or evidenced native pain, not a hypothetical feature |
| Candidate and role | Exact project/version/official repository; `REFERENCE`, `DEPENDENCY`, or `TOOL` |
| Legal/supply-chain | Verified license and attribution/redistribution obligations, provenance, maintenance and security posture |
| Native/platform fit | Flutter/Dart SDK and iOS/Android support, API/asset boundaries and release-mode constraints |
| Truth compatibility | Source task/choice IDs, grading/error, assistance, run/session, telemetry, earned vs skipped completion, XP, due/repair, privacy |
| Adoption economics | Estimated pilot + integration + proof + future maintenance compared with keeping current code; note uncertainty, realistic rollback |
| Recommendation | `PILOT`, `ADOPT_LATER`, `DEFER` or `DO_NOTHING`; owner decision needed before production writes |

Recommend one bounded pilot **only** if there is a persuasive expected total-value advantage, a safe rollback and a clear next-stage consumer. Do not claim 2× savings or fixed-day delivery without evidence.

**APK / reverse engineering boundary:** Observing publicly accessible app flows and analyzing software with appropriate permission can inform independent design; an APK does not yield a maintainable Flutter source project. Do not copy proprietary code, character/room imagery, UI assets or protected resources from competitors; comply with applicable law and licenses. Prefer official source releases, permissively licensed examples and SDKs.
